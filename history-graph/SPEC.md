## 1. 背景と目的

### 1.1 既存の Forma Issues の課題

- Forma（Autodesk Construction Cloud、以下 ACC）では、Issue の履歴（起票→対応→モデル更新→クローズの流れ）を時系列で追う手段が弱い。ステータス変更や担当変更の履歴は API で取得できない。
- Issue について比べられるのは、ピンを打った時点のサムネイル（スナップショット）と現在のモデルくらいしかない。モデルが何度も更新される間に、同じ指摘がどう扱われてきたかを確認できない。
- 実際の運用では、モデルの更新をまたいで Issue の関係者は設計者・監理者・施主・施工者と変わっていく。その間、同じ指摘が繰り返し出ていることも起こり得る。履歴を確認できれば、最適なアクション（再指摘ではなくエスカレーション、根本原因の追及）を取れる。

### 1.2 このアプリの目的

Issue 単位で「同じ指摘が時間と人の間をどう流れたか」を追跡できるようにする。具体的には、1つの Issue について、起票・コメント・ステータス／担当変更・モデル更新（版間の差分要約つき）を1本のタイムラインに並べ、モデル更新については 3D ビューア上で版同士の差分まで確認できるようにする。

### 1.3 機能概要

1. **Issue 一覧**：対象モデルの実 Issue を Issues API でライブ取得し、アプリ側で記録した履歴（変化イベント、モデル更新、派生指標＝Close/Reopen 回数・モデル更新件数）をマージして表示する。ページング／ソート／検索／ステータス絞り込み対応。既定の並びは表示番号の降順、既定の表示件数は10件とし、**初期選択は対象モデルにピンされた最新の Issue** とする（別モデルにピンされた Issue を初期選択にしない。UIUX レビュー H3 対応、2026-11-17）。
2. **タイムライン（履歴グラフ）**：選択した Issue の履歴を時系列に表示する。直上にピン時点のサムネイル（§7.4）を表示する。
3. **差分ビュー**：版ペアの diff（ファイル全体の件数＋ピン近傍の内訳）を表示する。版ペアはタイムラインのイベントからでも、ピッカーからでも（任意のペアを独立に）指定できる。**ペアを確定した時点で件数チップは「取得中」に差し替え、取得完了まで前ペアの数字を表示しない**（見出しのペアと数字のペアを食い違わせない。UIUX レビュー H1 対応、2026-11-17）。取得中にペアが切り替わった場合は、古い結果で画面を上書きしない。
4. **3D 差分ビューア**：版ペアの2モデルを APS Viewer に集約ロードし、diff の分類で色分け表示する（§7）。

## 2. 設計判断（デザイン v2、2026-11-17 ユーザー決定）

- **グラフの単位は Issue であり、Issue ごとに独立**している。Issue の ID は Forma 側で不変であることを前提とする。
- グラフの形：**Open = スタート、Close = ゴール（1周であって終わりではない）、Reopen は同じグラフの継続**。
- **モデル更新は、Issue の履歴の中のイベントの一種**として扱う（モデル更新そのものを追跡対象にはしない）。
- **モデル内の要素そのものは追跡しない**。要素の同一性判定、削除→再作成時の入替候補の提示・確定は対象外（初期案にあった候補確認フローは、ユーザーの指摘で撤回した）。
- **別 Issue として起票された指摘は、別 Issue として扱い切る**。Issue をまたぐ重複検出はしない（割り切りとしてユーザー承認済み）。
- モデル更新イベントにぶら下げる diff 要約は、ファイル全体の diff をピン近傍で絞った**表示上の絞り込み**であり、オブジェクト追跡ではない（§6.4）。

## 3. データ原則

- **表示データは全て実行時に API から取得する**。事前投入データ・モックデータは使わない（ユーザー指示 2026-11-17。実測ダンプ由来の「種キャッシュ」はこの指示で廃止した）。
- このアプリは「履歴の記録者」であり、状態の管理者ではない。**現在値は常に Forma 側が正**である。
- アプリ側が保持してよい状態は次の3種のみで、いずれも `data/` 配下に置き、GitHub には push しない。
  1. **スナップショット履歴**（`data/snapshots.json`）：Issue ごとの前回値（ステータス／担当者）と、変化イベントの追記型ログ。Forma の API が履歴を返さないための例外的な保持。
  2. **モデル版の検出状態**：どの版までをモデル更新イベントとして取り込んだか。
  3. **diff 実行時キャッシュ**（`data/diff-cache/`）：アプリ自身が実 API ジョブで取得した diff 結果の正規化キャッシュ。各ファイルに出所（ジョブ実行日時 `jobRunAt`・対象ペア・対象モデルの lineageId）を記録する。再利用はこのキャッシュのみとし、出所不明のデータを混ぜない。
- 認証情報（`.env`／`.token.json`）は git 管理外。トークンをリフレッシュした場合は、探索対象の全ての `.token.json` に書き戻す（運用ルール）。

## 5. イベントモデル

タイムラインに並ぶイベントは次の4種である。

| イベント | 取得方法 | 時刻の意味 |
|---|---|---|
| 起票 | Issues API（ライブ取得） | Issue の作成時刻 |
| コメント | Issues API（ライブ取得） | コメントの投稿時刻 |
| ステータス変更／担当変更 | **スナップショット差分で検出**：`POST /api/refresh`（および起動時）の取り込みで前回値と比較し、変化があればイベントを生成する | **検出時刻**であって実際の変更時刻ではない（画面にもその旨を明示する）。初回取り込みはベースライン記録のみでイベントは発生しない |
| モデル更新 | 対象モデルの版公開日時から生成（下記の2系統） | 版の公開時刻 |

モデル更新イベントの付与ルール：

1. **公開版ルール**：その Issue が開いている間に公開された版を、モデル更新イベントとして付ける。
2. **関連するモデル更新**：ピン付き Issue については上記に加えて、**そのアンカー要素が実際に変化した連続ペア**（例：V1→V2）を「関連するモデル更新」として付ける。判定はライブ diff の要素リストで行い、推測では付けない。追加／削除はリストへの含有で判定し、変更は §6.2 の変更判定（形状シグナルまたはプロパティ値の実変化）で判定する。これにより、Issue 作成より前に公開された版しか無い Issue でも、その指摘に関わる変更がタイムラインに現れる。判定中（diff ジョブ実行中）は「確認中」の仮イベントを表示し、完了後に自動で取り直す。
   - 実測での検証（旧アイテムの Issue #43〜47）：植栽追加・藤棚撤去・外灯移動・ドアのプロパティ変更はいずれも V1→V2 が、室名変更＋壁移動は V2→V4 のみが付与され、誤付与はなかった。

将来は Issues の Webhook（`issue.updated-1.0` 等）でスナップショット検出をリアルタイム化する想定だが、現行はポーリング方式である（§9）。

## 6. diff 仕様

### 6.1 取得方式

- diff は **Model Properties API** の index＋diff ジョブを、アプリが実行時に回して取得する。**3-legged トークンが必須**であり、2-legged では 403 になる（実測）。
- 対象モデルの各版について index を構築し（Snowdon Architectural で 36,131 オブジェクト）、版ペアの diff ジョブ結果を正規化して実行時キャッシュに保存する（§3）。
- diff 行の構造（実測）：`{type: OBJECT_ADDED|OBJECT_REMOVED|OBJECT_CHANGED, svf2Id, externalId, props, prev, propsHash, geomHash, bboxMin, bboxMax, location}`。`location` は全行 (0,0,0) で未投入であり、**要素の移動は独立した行種別ではなく、OBJECT_CHANGED 内の bbox 平行移動と geomHash 変化として現れる**。

### 6.2 変更判定とロケールノイズの除外

diff の生の「変更」件数は、そのままでは実変更を表さない。英語ロケールの Revit で作られたモデルを日本語ロケールで再保存すると、パラメータ名・カテゴリ名のローカライズでフィールドキーのハッシュが変わり、ほぼ全要素が「変更」に計数されるためである。実測の根拠（出典：`research/v2-diff-measurement.md` §5・§8）：

| ペア | 追加 | 削除 | 変更 | 備考 |
|---|---|---|---|---|
| V1→V2（旧アイテム、跨ロケール） | 450 | 450 | 34,718 | ユーザーの実変更4点を含む |
| V1→V5（対照：V1 を無変更で日本語再保存） | 449 | 449 | 34,719 | **無変更でも変更は約3.4万件**。bbox 純平行移動は **0件**、geomHash 変化は **63件**のみ。追加／削除の正体はビュー／セッション系要素の ID 再生成（英語名→日本語名の対称形） |
| V5→V2（日本語保存同士） | 34 | 34 | 267 | ノイズが約99%消え、実変更4点がピンポイントで分離できる |
| V2→V4（日本語保存同士、実質 V2→V3） | 51 | 33 | 374 | 室名変更＋壁移動を含む |

このため、本アプリの「変更」判定は次のいずれかに限定する：

- **形状シグナル**：geomHash の変化、または bbox の移動がある。
- **プロパティ値の実変化（valueChanged）**：キーの付け替えではなく、値そのものが変わっている。

実測では、V1→V2 の変更 34,718 件のうち valueChanged と判定されたのは **392 件のみ**であり、形状シグナル（geomHash 変化）は **106 件**、bbox が純平行移動した行は **ちょうど2行**（移動した外灯2基、移動量 (−1.671, +3.424, 0) ft）だった。なお geomHash 変化には再テッセレーション由来の残差があり、無変更再保存でも 63 件出る（ノイズフロア）。件数だけで実変更を断定しないこと。

### 6.3 geometry／all モード

`GET /api/diff/elements` の `mode` で、3D 表示に使う「変更」要素の範囲を切り替える。

- `geometry`（既定）：「変更」は形状シグナルのある要素のみ。プロパティのみの変更は 3D 色分けの対象にしない（§7.3）。
- `all`：プロパティのみの変更（valueChanged）も含める。

追加／削除は両モード共通である。関連ペア判定（§5）では、プロパティのみの変更も「変化」として扱う（モードとは独立）。

### 6.4 ピン近傍の定義

モデル更新イベントの diff 要約は、ファイル全体の件数に加えて「ピン近傍」の内訳を表示する。

- Issues API のピン座標は **Viewer 座標系**、diff の bbox は **Revit 共有座標系**であり、座標同士を直接比較できない。さらにピンは要素上の一点であって中心ではない。
- このため本アプリでは、**ピン対象要素（アンカー要素）自身の bbox 中心**を基準点とし、**水平 30ft 以内・上下 ±6ft** の範囲に入る diff 行を近傍として数える。
- アンカー要素がそのペアの diff に現れない場合は、取得済みの他のペアの diff における同要素の bbox で代用する。それも無い場合はファイル全体の件数のみを返し、その旨を明示する。
- 近傍判定はヒューリスティクスであり、近傍の変更が「その Issue の修正である」とは限らない（画面・文書でその前提を崩さない）。
- **対象要素の表示（UIUX レビュー H2 対応、2026-11-17）**：アンカー要素自身がそのペアでどう変化したか（追加／削除／変更、形状シグナル・移動・値変化の別、変更プロパティ）は、近傍リストとは別に**先頭の固定ブロック**で表示する。アンカーがそのペアの diff に現れない場合は「対象要素自体に変更はない」旨を明示した上で同じ位置に出す。アンカー自身の行は近傍リスト側には重複させない。
- **近傍リストのグループ化（同上）**：近傍リストは、種別＋基底名（要素名から末尾の `[要素ID]` を除いたもの）＋変更プロパティ＋シグナル有無が同じ行をグループ化し、「基底名 ほか ○件」として折りたたみ表示する（同種要素の繰り返しで対象が埋没しないようにするため）。
- **bbox を持たない要素の変更（同上）**：部屋などの bbox を持たない要素は近傍判定に入らないため、ファイル全体の「bbox を持たない modified で実変化シグナル（形状・移動・値変化）がある要素」を基底名でグループ化し、別枠で返す（`noBbox`）。室名変更のような値変化はここに現れる。

## 7. ビューア仕様（3D 差分表示）

### 7.1 集約ロードと色分け

- 版ペアの2モデルを、1つの APS Viewer に集約ロードする（`keepCurrentModels`）。読み込み済みモデルは版単位で再利用し、ペア切替時は不要な版だけを unload する。
- **表示用 viewable は「New Construction」を版ごとに名前で解決する**（環境変数 `HG_VIEWABLE_NAME`、既定 `New Construction`）。geometry guid は版間で変動するため guid 直指定はしない（`HG_VIEWABLE_GUID` は明示指定時のみ使う上書き）。解決順は ①guid 明示指定 ②名前の完全一致 ③名前の部分一致 ④バウンディングボックス体積が最大の 3D viewable ⑤`getDefaultGeometry()`。経緯と実測は §8。
- 分類は externalId→dbId の対応付けで適用する（アンカー解決も externalId 経由を維持する。metadata の objectid とインデックスの svf2Id には +1 のずれがある実測があるため、objectId 直指定には寄せない）：
  - 変更なし：新版のみ表示（旧版の同要素は重ねない）
  - **追加：新版の要素を緑**
  - **削除：旧版の要素のみを、赤のテーマカラー（alpha 0.45）のゴースト**で表示
  - **変更：新版の要素を黄**。旧版はトグルで alpha 0.35 のゴースト表示にできる
- カメラは対象要素（Issue のアンカー要素、無ければ変更要素全体）へ §7.5 の方式で寄せる。

### 7.2 Before／After の明示

- ビューア脇に**凡例を常時表示**する。「Before = V{n}（旧版）」「After = V{m}（新版）」を版番号入りで示し、各分類（追加／削除／変更）がどちらの版の要素をどう描くかを明記する。版ペアを変更すると凡例の版番号も追従する。
- **表示モード切替**：「重ねて表示」「Before のみ」「After のみ」を切り替えるボタンを置く。Before のみでは旧版モデルだけが（変更要素は旧版の姿で）、After のみでは新版モデルだけが表示され、切り替えて見比べられる。切替は分類済みの結果を使い回し、再取得はしない。

### 7.3 UX の方針（段階ロード／差分フォーカス／all モード）

1. **差分フォーカスを既定表示**とする（2026-11-17 に定義を変更）：変更のない要素は**文脈として残し**、対象（アンカー要素／変更要素）への視線を遮る部材だけをゴースト化して見通しを確保する（§7.5）。変更要素には引出線ラベルを付ける（§7.6）。「全体表示」に切り替えると透明化も引出線も無い素の重ね表示になる。Before のみ／After のみモードとも両立させる。旧定義（変更要素とその周辺以外を全部隠す）は、文脈が失われて変更の意味が読めないため廃止した。
2. **段階ロード**：まず After（新版）だけを先に読み込んで表示し、操作可能な状態にする（件数サマリーは diff の結果で先に出す）。Before（旧版）は裏で読み込み、揃った時点で分類・色分けを適用する。進捗は段階表示する（After 表示中→Before 読み込み中→色分け適用済み）。Before のロード完了でユーザー操作をブロックしない。
3. **all モードでは 3D 色付けをしない**：`all` モードではテーマカラー適用を行わず（34,718 件規模の色付けが重さの主因のため）、件数と要素リストのみとし、3D 側には「色分けは geometry モードのみ」の注記を出す。geometry モードの色分けは §7.1 のとおり維持する。

### 7.4 ピン時点サムネイル

- タイムラインの**直上**に、その Issue がピンされた時点のサムネイルを表示する。取得経路は Issues API の `issue.snapshotUrn`（OSS オブジェクト）であり、サーバ側プロキシ（`GET /api/issues/:id/thumbnail`、署名付き URL 経由）で配信する。
- `snapshotUrn` が無い Issue では、プレースホルダは出さず表示自体を省略する（§9）。

### 7.5 カメラと見通し（sample-d の表示方式）

ビューアの表示方法は、ビューアアプリ sample-d（`demo-issues-3d/app/SPEC.md` §6.5〜§6.7）で実証済みの方式に合わせる。差分固有の色分け・Before／After 凡例・表示モード（§7.1〜§7.2）は維持する。

- **カメラ**：対象要素の中心にピボットを置く（`setView` はピボットを動かさないため先に移す）。方位は現在のカメラの方位角だけを維持し、**仰角は 28° 固定**、上方向はワールド Z。距離は対象ボックスの半径／tan(fov/2)×1.9。移動はイージング（easeInOutCubic）付きグライド（所要 0.65〜1.2 秒、移動量で可変）で、ビューアへのユーザー入力（pointerdown／wheel）で即キャンセルする。`prefers-reduced-motion` 時と移動量が僅少なときは即時移動にする。対象要素のボックスが取れない場合はピン座標を注視点とする代替フィットを使う。
- **見通し確保（occluder removal）**：`viewer.setGhosting(true)` のうえで、カメラ→対象ボックス（「手前を消す範囲」で拡大）の 8 隅＋中心への 9 本の視線と交差する要素だけを `hide()` する（フレームが残るため完全には消えない）。対象自身・分類済み要素（追加／削除／変更）とその祖先は候補から除外する。範囲スライダは 0〜100%（既定 50%＝ボックス 2 倍、localStorage に保存）。0% で無効。
- 遮蔽物の集合は**静的**とする：フォーカス時点の視点で 1 回だけ計算し、カメラ移動では再計算しない。再計算するのは分類の適用・グライド到着・スライダ変更・引出線ラベルのクリックで対象が変わったときだけ。適用は前回との差分だけを表示／非表示する（全表示→全非表示の往復によるチラつきを避ける）。ステータスに「手前の部材 N 件を透明にして見通しを確保」と件数を出す。

### 7.6 引出線ラベル

細かい変更はゴーストの透明度では判読できないため、変更要素を引出線（リーダーライン）で明示的に指す。

- **対象**：差分フォーカス表示時（geometry モード）に限る。変更要素（追加／削除／変更）それぞれに、その要素の 3D 位置（ボックス中心）からラベルへ線を引き、ラベルに変更種別と要素名を示す。削除要素は Before 側の位置を指す。
- **上限**：最大 **12 件**。Issue のアンカー要素を先頭に固定し、残りはアンカー（無ければ変更要素全体の重心）からの距離順に選ぶ。ラベルをクリックするとその要素へカメラが寄り、見通しの対象もその要素に移る。
- **配置**（sample-d のマーカー処理 §6.6 と同じ）：ラベルは画面中央のゾーン（左右 12.5%〜87.5%、上下 18%〜74%）の外側の余白帯に逃がし、辺ごとに詰めて最小間隔 6px を確保し、四隅の衝突も解消する。アンカー候補点がカメラの後ろ・画面外の要素はラベルごと隠す。ラベルサイズは構築時に 1 回だけ測ってキャッシュし、カメラ移動への追随は transform のみの書き換え＋rAF 集約で行う（強制リフローによるチラつきを招かない）。

### 7.7 3D 確認は必須ステップ（選択と同時に読み込み開始）

- 3D モデル確認は任意の付加機能ではなく業務フローの必須ステップとして扱う。**Issue を選択した時点で Viewer の初期化と対象モデルの読み込みを即座に開始**し（差分件数の取得を待たない）、ユーザーが 3D を見ようとしたときには表示済みになっている状態を目指す。アプリ起動直後の初期選択 Issue についても同じである。
- 選択中 Issue にモデル更新イベント（関連ペア含む）がある場合は、そのペアが先読み対象になる。読み込みは段階ロード（§7.3-2、After 優先）のままバックグラウンドで行い、一覧やタイムラインの操作はブロックしない。読み込み状態の表示は段階ステータスを流用する。

### 7.8 モデル更新時の自動スクショ（サーバ側撮影）

新しい版の公開を検出したとき、変更箇所を**サーバ側だけで**撮影する（ユーザーのクライアントアプリは不要）。

- **方式**：アプリが新しい版の公開を検出したとき（refresh／スナップショットの版検出フロー。既知の版一覧との差分で判定し、初回は基準として記録するだけで遡らない）、新ペア（直前版→新版）の撮影ジョブをキューに入れる。撮影はサーバ側のヘッドレス Chrome（DevTools プロトコルで駆動）が撮影ページ（`public/capture.html`）を開き、APS Viewer で §7.1〜§7.6 と同じ見た目（色分け＋見通し確保＋引出線ラベル）を描いて `getScreenShot` で撮影し、PNG をサーバへ送る。描画の安定を待ってから撮影する。
- **前提条件**：撮影ホストから Autodesk の Viewer CDN と APS エンドポイントへ到達できること。開発 VM は Viewer CDN に到達できないため、VM では撮影パイプライン（検出→キュー→撮影試行→保存→表示）の動作までを検証範囲とし、実撮影の画は到達可能なホスト（ユーザーの実機など）での確認事項とする。失敗した撮影はジョブログ（`data/captures/index.json`）に理由つきで残し、refresh 本体は壊さない。
- **撮影対象**：①そのペアでアンカー要素が変化した、**開いている**ピン付き Issue のアンカー箇所（最優先）。②その他 geometry 変化要素（bbox を持つ追加／削除／形状変化・移動）は近接クラスタ単位（中心間 40 以内を同じ画にまとめ、1 クラスタ最大 25 件）で、クラスタ数の上限は **5 件**（`HG_CAPTURE_MAX_CLUSTERS`）。
- **カメラ**：①のうち、ピンがカメラ（viewerState）を持つ場合は**ピンカメラ再現**——ピンが保持する視点・注視点・上方向をそのまま使う（ピンした瞬間にユーザーが見ていた画と変更後の画が同じ視点で揃うのが目的。直交投影の指定がある場合は投影方式も合わせるが、画角の厳密な再現はベストエフォート）。viewerState が無いピン（**API 作成ピンは viewerState が空**という実測がある。HG の #48〜52 は全てこちら）については**代替カメラ**——ピン位置を注視点とし、方位 45°・仰角 28°・距離 60 の定義済みカメラで撮影する。各スクショのメタデータ（ジョブ記録の `camera`）で「ピンカメラ再現（`pin`）／代替カメラ（`fallback`）」を区別できるようにする。②のクラスタ撮影は sample-d 方式の**計算カメラ**（ピボット＝対象の中心、方位は初期カメラを維持、仰角 28°）を使う。
- **保存と表示**：PNG は `data/captures/` に保存し、ジョブ記録（ペア・対象要素・カメラ種別・成否・理由）を `data/captures/index.json` に持つ。タイムラインのモデル更新イベントの下にサムネイル表示し（クリックで拡大）、撮影の成否・件数もイベントに表示する。運用のための手動実行エンドポイント `POST /api/captures/run`（{from, to}）も用意する。
- **設定**：`HG_CAPTURE_ENABLED=0` で無効化（既定は有効）。Chrome は `HG_CHROME_PATH` で指定でき、未指定時は Playwright の Chromium → `/opt/meta-chromium/chrome` → PATH 上の Chrome の順に探す。

## 9. 既知の制約

- **コメント**：対象プロジェクトの実 Issue は、当初は Forma の画面から付けられたコメントが**全件0件**だった。そのため旧アイテム側のタイムラインは起票・モデル更新・スナップショット検出イベントが主になる。HG の Issue #48〜52 には API 経由で投稿した実コメントがあり、自動的にタイムラインに表示される。コメントが付いた Issue が現れれば同様に表示される。
- **サムネイル**：`snapshotUrn` を持つのは Forma の画面から作られた Issue のみで、実 Issue のうち取得できたのは **3件**（#1・#3・#24、2026-11-17 時点）。**API 経由で作成したピンの Issue は `snapshotUrn` が無く、サムネイル表示はない**。
- **ピン座標は近似**である：API 作成ピンの座標は要素の bbox 中心から算出したもので、精度は ±数 ft。カメラ fit の用途には十分だが、厳密なクリック点ではない。
- **APS の index 構築には時間がかかる場合がある**（通常は版あたり 15〜30 秒程度だが、実測で約20分を要したことがある）。アプリのジョブは自動リトライで完走させる。
- **Viewer の実描画は開発 VM から検証できない**（Viewer CDN に到達不可）。集約ロード・色分け・ゴースト・表示モード切替の見た目は、実機ブラウザでの確認を前提とする。VM ではエンドポイント応答・件数の一致と、Viewer API 呼び出し列（状態遷移）までを検証範囲とする。
- **自動スクショの実撮影も開発 VM では検証できない**（同じく Viewer CDN に到達不可のため）。VM では検出→キュー→撮影試行→失敗理由つきの記録→タイムライン表示までのパイプラインを検証し、実撮影の画は到達可能なホストでの確認事項とする（§7.8）。
- Issue・版の削除は API にない。作り直しは新規作成で代替し、旧データは残置する（§8）。
- 未実装・範囲外：Webhook によるリアルタイム検出、Issue の作成・編集（本アプリは読み取り専用）、AEC Data Model 連携、Issue をまたぐ重複検出（§2 の割り切り）。
