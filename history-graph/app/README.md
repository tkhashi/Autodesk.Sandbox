# 履歴グラフ実アプリ v1（history-graph-app）

Forma（ACC）Issues の「生涯」を追う実アプリです。UIモック（`history-graph/ui-mock/`）のレイアウトと
sample-d（Issues 3D デモ）の流儀を土台に、モックデータを実 API に差し替えました。

- **Issue の現在値**は常に Forma から実取得（Issues API）
- **状態変更・担当変更の履歴**は Forma の API では返らないため、アプリ側のスナップショットで記録
- **モデル更新イベント**は Snowdon Towers Sample Architectural.rvt の版公開日時から差し込み
- **版間の差分**は Model Properties Diff を実行時に実 API ジョブで取得します。
  **データは全て実行時に API から取得し、事前投入データ（実測ダンプ等）は使いません。**
  ジョブ結果は出所（ジョブ実行日時・対象ペア）つきで実行時キャッシュに保存して再利用します

対象プロジェクト: Snowdon Towers（`b.031a6e68-ccdf-4a29-b8a5-50a2a3ecac25`）
対象モデル: Snowdon Towers Sample Architectural.rvt（lineage `VwJ57NkiQ-Gy0nHLR3UmAA`）

## 起動手順

前提（sample-d と同じ APS アプリ・認証情報を使います）:

1. `.env` に `APS_CLIENT_ID` / `APS_CLIENT_SECRET`（sample-d の `demo-issues-3d/app/.env` と同じもの）
2. `.token.json` に 3-legged トークン（refresh token を含むもの。sample-d と同じもの）

`.env` / `.token.json` がアプリ直下に無い場合は、次の順で探索して自動利用します:
①clone 配置で隣にある sample-d（`../../sample-d-issues-3d/`）
②ワークスペース内の `forma-hands-on/demo-issues-3d/app/` と `sample-a-http-client/`。
どれにも無い場合は、コピー手順の案内を表示して終了します。
**トークンをリフレッシュした場合は、探索対象の全ての `.token.json` に書き戻します**（運用ルール）。

```bash
cd history-graph-app
node server.mjs          # 依存パッケージなし（Node 18+）
# → http://localhost:3100 （PORT 環境変数で変更可）
```

起動時に一度スナップショット取り込みが走ります。以後の取り込みは画面右上の
「履歴を取り込む（スナップショット）」ボタン、または `POST /api/refresh` で行います。

## 画面

- **Issue 表**: 実 Issue（Snowdon Towers）。ページング（既定 5 件、5/10/25/50/100）、
  ヘッダクリックのソート（昇順→降順→解除、空値は常に後ろ）、検索、ステータスのチップ絞り込み。
  ステータスは sample-d と同じ色バー＋英語表記。行にはミニ履歴グラフと
  Close/Reopen 回数・モデル更新件数のバッジが出ます。
- **右カラム（タイムライン）**: 直上に、Issue がピンされた時点のサムネイル
  （Forma が Issue 作成時に保存したビュー画像。Issues API の `snapshotUrn` をサーバ側プロキシで配信。
  画像が無い Issue では表示自体を省略します）。
  起票 → コメント（実 API）→ 状態変更／担当変更
  （スナップショット由来。検出時刻である旨を明示）→ モデル更新 → Close 🏁 ／ Reopen → 現在。
  Open がスタート、Close がゴール（ラップ）、Reopen で同じグラフが続きます。
  別 Issue として切り出された指摘は別の Issue として扱います（設計 v2 の決定）。
  - **関連するモデル更新**: ピン付き Issue については、「開いている間に公開された版」の
    イベントに加えて、**そのアンカー要素が実際に変化した連続ペア**もイベントとして付けます
    （Issue 作成より前に公開された版しか無い Issue でも、その変更がタイムラインに現れます）。
    判定はライブ diff の要素リストで行います。追加／削除はリストへの含有で判定し、
    変更は「形状シグナル（形状ハッシュ変化・bbox 移動）があるか、プロパティ値の実変化があるか」
    で判定します。後者はロケール再保存ノイズ（キー付け替えのみで値が同じ行）を除外するための
    フィルタで、実測では V1→V2 の変更 34,718 件中、値の実変化と判定されたのは 392 件でした。
    判定中（diff ジョブ実行中）は「確認中」の仮イベントを表示し、完了後に自動で取り直します。
- **差分ビュー**: タイムラインのモデル更新／関連イベントを選ぶと、その版ペアの diff を表示。
  ファイル全体の件数（追加／削除／変更）＋ピン周辺の内訳（テキスト）。
  **版ペアのピッカー**（From／To のセレクト＋「差分を表示」）もあり、Issue やイベントの
  選択とは独立に任意のペア（例: V1→V4）を指定して差分確認できます。モデル更新イベントを
  選んだときは、そのペアがピッカーの初期値になります。
- **3D ビューア（差分）**: 版ペアの2モデルを1つの APS Viewer に集約ロードし、diff の要素リストで
  表示を振り分けます。変更なしは新版のみ／追加は新版のみ・緑／削除は旧版のみ・赤ゴースト／
  変更は新版・黄（旧版はトグルでゴースト）。ピン対象要素があればそこへフィットします。
  「変更」の 3D 表示対象は既定では形状シグナル（形状ハッシュ変化・bbox 移動）のある要素のみで、
  プロパティのみの変更まで含める場合はトグルで切り替えます（画面上にも明示）。
  - **Before／After の明示**: ビューア脇に凡例を常時表示します。「Before = V{n}（旧版）」と
    「After = V{m}（新版）」を版番号入りで示し、追加／削除／変更の各分類がどちらの版の要素を
    どう描くかを書きます。版ペアを変えると凡例の版番号も追従します。
  - **Before／After の表示切替**: 「重ねて表示」「Before のみ」「After のみ」を切り替える
    ボタンがあります。Before のみでは旧版モデルだけが（変更要素は旧版の姿で）、After のみでは
    新版モデルだけが（変更要素は新版の姿で）表示されるので、切り替えて見比べられます。
    切替は分類済みの結果を使い回すため、モデルも要素リストも再取得しません。
  Viewer の CDN に到達できない環境では読み込めません（VM からは到達不可のため描画未検証。実機ブラウザで確認してください）。

## API

| エンドポイント | 内容 |
|---|---|
| `GET /api/issues` | 実 Issue 一覧＋アプリ側履歴（変化イベント、モデル更新、派生指標）をマージして返す |
| `GET /api/issues/:id/comments` | コメントを実 API から取得 |
| `GET /api/issues/:id/thumbnail` | ピン時点のサムネイル画像（`snapshotUrn`）をサーバ側プロキシで配信。無い Issue では 404 |
| `GET /api/versions` | Architectural の版一覧（V1〜V4、公開日時つき）を DM API から取得 |
| `GET /api/diff?from=&to=&issue=` | 版ペアの diff。実行時キャッシュがあればそれを返し、無ければ実 API ジョブを開始（202 で状態を返し、完了後に再取得で結果）。`issue` を付けるとピン周辺の内訳も返す |
| `GET /api/diff/elements?from=&to=&mode=` | 3D 差分表示用の要素 ID リスト（added／removed／changed の externalId・SVF2Id）。`mode=geometry`（既定）は「変更」を形状シグナルのある要素のみに絞り、`mode=all` はプロパティのみの変更も含む。diff が未取得なら 202 でジョブ状態を返す |
| `POST /api/refresh` | スナップショット取り込みを実行 |
| `GET /api/token` | APS Viewer 用の 2-legged トークン |

## 状態管理の設計（スナップショット方式）

このアプリは「履歴の記録者」であり、状態の管理者ではありません。現在値は常に Forma が正です。
アプリ側が持つのは `data/` の中だけです（GitHub には push しません）。

- `data/snapshots.json` — Issue ごとの前回値（status／担当者）と、変化イベントの追記型ログ。
  起動時と `POST /api/refresh` で全件取得し、前回値と比較してイベントを生成します。
  **イベントの時刻は「検出時刻」であって実際の変更時刻ではありません**（画面にも明示）。
  初回取り込みはベースライン記録のみで、イベントは発生しません。履歴は運用を続けるほど溜まります。
- `data/diff-cache/` — このアプリ自身が実 API ジョブ（Model Properties の index＋diff）で取得した
  diff 結果の正規化キャッシュ（format 3。変更行には形状シグナルに加えて「プロパティ値の実変化」
  フラグを持ち、関連ペア判定に使います）。各ファイルにジョブ実行日時（`jobRunAt`）と対象ペアを記録します。
  ここに無いペアは、初回アクセス時にジョブを実行して取得します（202 応答で状態を返し、完了後に結果を返す）。

将来は Issues の Webhook（`issue.updated-1.0` 等）で検出をリアルタイム化する想定で、
その場合も「前回値との比較でイベント化する」核はそのまま使えます。今回はポーリング方式です。

## diff の取得（全て実行時 API）と実測値との対応

**データは全て実行時に API から取得します。事前投入データは使いません。**
diff は、アプリが Model Properties API の index＋diff ジョブをその場で実行して取得し、
結果だけを実行時キャッシュ（`data/diff-cache/`、ジョブ実行日時つき）に保存します。

参考として、同じジョブで取得できる統計は過去の実測（`research/v2-diff-measurement.md`）と一致します:

| ペア | 追加 | 削除 | 変更 | bbox を持つ行 |
|---|---|---|---|---|
| V1 → V2 | 450 | 450 | 34,718 | 7,092 |
| V2 → V4（実質 V3） | 51 | 33 | 374 | 158 |
| V1 → V4 | 468 | 450 | 34,718 | 7,092 |

注意（実測で判明したこと）:

- **「変更」34,718 件の大半はロケールノイズ**です。英語ロケールの Revit で作られたモデルを
  日本語ロケールで再保存すると、パラメータ名等の表記差でほぼ全要素が「変更」になります。
  日本語保存同士の V2→V4 では変更は 374 件まで減りました。実際に形が変わった目安は、
  形状ハッシュ変化・bbox 移動のある「形状シグナル」の件数です（画面でも併記）。
- **V3 は登録ファイルが破損しており変換できません**（内容の実体は V4）。そのため V4 の
  モデル更新イベントの diff は V2→V4 ペアで表示します。
- ピン近傍の絞り込み: Issues API のピン座標は Viewer 座標系、diff の bbox は Revit 共有座標系で、
  しかもピンは要素上の一点（中心ではない）ため、座標同士を直接は比較できません。
  本アプリでは「ピン対象要素の bbox 中心（共有座標系）」をアンカーに、水平 30ft 以内・
  上下 ±6ft の行を数えます（viewer-mock と同じ基準）。対象要素がそのペアの diff に
  現れない場合は、このアプリが取得済みの他のペアの diff の bbox で代用し、それも無い場合は
  ファイル全体の件数のみ返してその旨を明示します。近傍判定はヒューリスティクスであり、
  「その Issue の修正」とは限りません。

## 既知の制約

- **対象プロジェクト（Snowdon Towers）の実 Issue はコメントが全件 0 件**のため、実データの
  タイムラインは起票・モデル更新・スナップショットで検出した変化イベントが主になります。
  コメントが付いた Issue が現れれば自動的にタイムラインに表示されます。
- ピン時点のサムネイル（`snapshotUrn`）が取得できるのは実 Issue のうち 3 件のみです
  （2026-11-17 時点。Forma の画面から作られた Issue だけが画像を持ちます）。無い Issue では表示を省略します。
- APS Viewer の描画は、Viewer の CDN に到達できる環境（実機ブラウザ）でのみ確認できます。
