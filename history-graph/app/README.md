# 履歴グラフ実アプリ v1（history-graph-app）

Forma（ACC）Issues の「生涯」を追う実アプリです。UIモック（`history-graph/ui-mock/`）のレイアウトと
sample-d（Issues 3D デモ）の流儀を土台に、モックデータを実 API に差し替えました。

- **Issue の現在値**は常に Forma から実取得（Issues API）
- **状態変更・担当変更の履歴**は Forma の API では返らないため、アプリ側のスナップショットで記録
- **モデル更新イベント**は Snowdon Towers Sample Architectural HG.rvt の版公開日時から差し込み
- **版間の差分**は Model Properties Diff を実行時に実 API ジョブで取得します。
  **データは全て実行時に API から取得し、事前投入データ（実測ダンプ等）は使いません。**
  ジョブ結果は出所（ジョブ実行日時・対象ペア）つきで実行時キャッシュに保存して再利用します

対象プロジェクト: Snowdon Towers（`b.031a6e68-ccdf-4a29-b8a5-50a2a3ecac25`）
対象モデル: **Snowdon Towers Sample Architectural HG.rvt**（lineage `n1BdFAarT-ajJkQvheK5EA`）

> **対象モデルについて（2026-11-17 切り替え）**: 本アプリの向き先は、正規ルートで作り直した
> 新アイテム「Snowdon Towers Sample Architectural **HG**」です。HG は V1（V1 無変更＋日本語再保存の
> 対照ファイル）に対して Issue を先に起票し、その後に V2（変更4点）・V3（室名変更＋壁移動）が
> 公開される順序で構成されているため、モデル更新イベントが各 Issue のタイムラインに自然に付きます。
> 旧アイテム（Snowdon Towers Sample Architectural.rvt）と旧 Issue #43〜47 は API では削除できないため
> ACC 上にそのまま残っていますが、本アプリの対象外です。対象は環境変数
> `HG_LINEAGE_ID` / `HG_ITEM_NAME` / `HG_VIEWABLE_NAME` で切り替えできます
> （旧アイテムに戻す場合: `HG_LINEAGE_ID=VwJ57NkiQ-Gy0nHLR3UmAA`）。
> 表示用 viewable は「New Construction」（全カテゴリ）を版ごとに名前で解決します
> （従来の「Coord - Arch Walls」は壁のみで、扉・藤棚・植栽等が含まれていませんでした）。

## 起動手順

前提（sample-d と同じ APS アプリ・認証情報を使います）:

1. `.env` に `APS_CLIENT_ID` / `APS_CLIENT_SECRET`（sample-d の `demo-issues-3d/app/.env` と同じもの）
2. `.token.json` に 3-legged トークン（refresh token を含むもの。sample-d と同じもの）

`.env` / `.token.json` がアプリ直下に無い場合は、次の順で探索して自動利用します:
①clone 配置で隣にある sample-d（`../../sample-d-issues-3d/`）
②ワークスペース内の `forma-hands-on/demo-issues-3d/app/` と `sample-a-http-client/`。
どれにも無い場合は、コピー手順の案内を表示して終了します。
**トークンをリフレッシュした場合は、探索対象の全ての `.token.json` に書き戻します**（運用ルール）。

```bash
cd history-graph-app
node server.mjs          # 依存パッケージなし（Node 18+）
# → http://localhost:3100 （PORT 環境変数で変更可）
```

起動時に一度スナップショット取り込みが走ります。以後の取り込みは画面右上の
「履歴を取り込む（スナップショット）」ボタン、または `POST /api/refresh` で行います。

## 画面

- **Issue 表**: 実 Issue（Snowdon Towers）。ページング（既定 10 件、5/10/25/50/100）、
  既定の並びは表示番号の降順（新しい Issue が先頭）。ヘッダクリックのソート（昇順→降順→解除、
  空値は常に後ろ）、検索、ステータスのチップ絞り込み。
  ステータスは sample-d と同じ色バー＋英語表記。行にはミニ履歴グラフと
  Close/Reopen 回数・モデル更新件数のバッジが出ます。
  初期選択は、対象モデル（HG）にピンされた最新の Issue が既定です（別モデルにピンされた
  Issue が初期選択になることはありません）。
- **右カラム（タイムライン）**: 直上に、Issue がピンされた時点のサムネイル
  （Forma が Issue 作成時に保存したビュー画像。Issues API の `snapshotUrn` をサーバ側プロキシで配信。
  画像が無い Issue では表示自体を省略します）。
  起票 → コメント（実 API）→ 状態変更／担当変更
  （スナップショット由来。検出時刻である旨を明示）→ モデル更新 → Close 🏁 ／ Reopen → 現在。
  Open がスタート、Close がゴール（ラップ）、Reopen で同じグラフが続きます。
  別 Issue として切り出された指摘は別の Issue として扱います（設計 v2 の決定）。
  - **関連するモデル更新**: ピン付き Issue については、「開いている間に公開された版」の
    イベントに加えて、**そのアンカー要素が実際に変化した連続ペア**もイベントとして付けます
    （Issue 作成より前に公開された版しか無い Issue でも、その変更がタイムラインに現れます）。
    判定はライブ diff の要素リストで行います。追加／削除はリストへの含有で判定し、
    変更は「形状シグナル（形状ハッシュ変化・bbox 移動）があるか、プロパティ値の実変化があるか」
    で判定します。後者はロケール再保存ノイズ（キー付け替えのみで値が同じ行）を除外するための
    フィルタで、実測では V1→V2 の変更 34,718 件中、値の実変化と判定されたのは 392 件でした。
    判定中（diff ジョブ実行中）は「確認中」の仮イベントを表示し、完了後に自動で取り直します。
- **差分ビュー**: タイムラインのモデル更新／関連イベントを選ぶと、その版ペアの diff を表示。
  ファイル全体の件数（追加／削除／変更）＋ピン周辺の内訳（テキスト）。
  **版ペアのピッカー**（From／To のセレクト＋「差分を表示」）もあり、Issue やイベントの
  選択とは独立に任意のペア（例: V1→V4）を指定して差分確認できます。モデル更新イベントを
  選んだときは、そのペアがピッカーの初期値になります。
  件数チップは、ペアを確定した時点で「取得中」に差し替わり、取得が終わるまで前ペアの
  数字は表示しません（見出しのペアと数字のペアが食い違う状態を作らないため）。
  ピン周辺の内訳は、**対象要素（アンカー）自身の変更を先頭の固定ブロック**で示し
  （そのペアで対象要素自体に変更が無い場合は、その旨を明示します）、周辺リストでは
  同種要素の繰り返しを「基底名 ほか ○件」に**グループ化して折りたたみ**ます。
  また、bbox を持たない要素（部屋など）は近傍判定に入らないため、ファイル全体の
  「位置（bbox）を持たない要素の変更」を別枠でグループ表示します（室名変更はこちらに
  現れます）。
- **3D ビューア（差分）**: 版ペアの2モデルを1つの APS Viewer に集約ロードし、diff の要素リストで
  表示を振り分けます。変更なしは新版のみ／追加は新版のみ・緑／削除は旧版のみ・赤ゴースト／
  変更は新版・黄（旧版はトグルでゴースト）。表示用 viewable は「New Construction」を
  版ごとに名前で解決します（§SPEC 7.1）。カメラは対象要素の中心にピボットを置き、
  方位を維持して仰角 28° 固定でグライドします（sample-d 方式。ユーザー入力で即キャンセル）。
  「変更」の 3D 表示対象は既定では形状シグナル（形状ハッシュ変化・bbox 移動）のある要素のみで、
  プロパティのみの変更まで含める場合はトグルで切り替えます（画面上にも明示）。
  3D 確認は必須ステップとして扱い、**Issue を選択した時点で Viewer の初期化とモデル
  読み込みを即開始**します（件数の取得を待たない。初期選択の Issue も同様）。
  - **Before／After の明示**: ビューア脇に凡例を常時表示します。「Before = V{n}（旧版）」と
    「After = V{m}（新版）」を版番号入りで示し、追加／削除／変更の各分類がどちらの版の要素を
    どう描くかを書きます。版ペアを変えると凡例の版番号も追従します。
  - **Before／After の表示切替**: 「重ねて表示」「Before のみ」「After のみ」を切り替える
    ボタンがあります。Before のみでは旧版モデルだけが（変更要素は旧版の姿で）、After のみでは
    新版モデルだけが（変更要素は新版の姿で）表示されるので、切り替えて見比べられます。
    切替は分類済みの結果を使い回すため、モデルも要素リストも再取得しません。
  - **差分フォーカス（既定の表示範囲）**: 3D 表示の既定は「差分フォーカス」で、変更のない
    要素は文脈として残し、対象（アンカー要素／変更要素）への視線を遮る部材だけを
    ゴースト化して見通しを確保します（sample-d の occluder removal 方式。カメラ→対象
    ボックスの 9 本の視線と交差する要素のみ。「手前を消す範囲」スライダ 0〜100%・既定
    50% で調整でき、遮蔽物の集合はフォーカス時点の視点で固定します）。あわせて変更要素
    には**引出線ラベル**（種別＋要素名、最大12件、アンカー優先＋近傍の変更。画面外は
    隠し、重なりを避けて配置）を付けます。ビューア脇の「全体表示／差分フォーカス」
    ボタンで、透明化も引出線も無い素の全要素表示に切り替えられます。
    Before のみ／After のみモードでもフォーカスは効きます。
  - **段階ロード**: ペア表示ではまず After（新版）モデルだけを読み込んで表示し、その時点で
    操作可能にします（件数サマリーは diff エンドポイントの結果で先に出ています）。Before
    （旧版）は裏で読み込み、要素リストの取得も並行して進め、揃った時点で分類・色分けを
    適用します。進捗はステータスに段階表示します（「After を表示中 — Before を読み込み中」
    →「色分け適用済み」）。Before のロード完了を待たずにカメラ操作ができます。
  - **all モードでは 3D 色付けをしません**: 「変更」の範囲を all（プロパティのみの変更も
    含める）にした場合は、3D ビューアへのテーマカラー適用を行いません（34,000 件規模の
    色付けが重さの主因のため）。要素リスト自体も取得せず、3D 側は版ペアの素表示
    （Before／After のモデル単位切替のみ）になり、「色分けは geometry モードのみ」という
    注記を凡例と差分ビューに出します。all の件数と内訳はテキスト側で確認してください。
  Viewer の CDN に到達できない環境では読み込めません（VM からは到達不可のため描画未検証。実機ブラウザで確認してください）。

## API

| エンドポイント | 内容 |
|---|---|
| `GET /api/issues` | 実 Issue 一覧＋アプリ側履歴（変化イベント、モデル更新、派生指標）をマージして返す |
| `GET /api/issues/:id/comments` | コメントを実 API から取得 |
| `GET /api/issues/:id/thumbnail` | ピン時点のサムネイル画像（`snapshotUrn`）をサーバ側プロキシで配信。無い Issue では 404 |
| `GET /api/versions` | 対象モデルの版一覧（公開日時つき）を DM API から取得 |
| `GET /api/diff?from=&to=&issue=` | 版ペアの diff。実行時キャッシュがあればそれを返し、無ければ実 API ジョブを開始（202 で状態を返し、完了後に再取得で結果）。`issue` を付けるとピン周辺の内訳も返す |
| `GET /api/diff/elements?from=&to=&mode=` | 3D 差分表示用の要素 ID リスト（added／removed／changed の externalId・SVF2Id）。`mode=geometry`（既定）は「変更」を形状シグナルのある要素のみに絞り、`mode=all` はプロパティのみの変更も含む。diff が未取得なら 202 でジョブ状態を返す |
| `POST /api/refresh` | スナップショット取り込みを実行 |
| `GET /api/token` | APS Viewer 用の 2-legged トークン |
| `GET /api/captures?from=&to=` | 自動スクショのジョブ記録（ペアで絞り込み可） |
| `GET /api/captures/:id/image` | 撮影済み PNG の配信 |
| `POST /api/captures/run` | 自動スクショの手動実行（運用用。`{from, to}`） |
| `GET /api/issues/:id/pin-snapshot` | ピン時点スナップショット（ピン座標・対象要素のピン時点の状態・最新版との照合結果）。未生成では 404 |
| `POST /api/sim/webhook` | 起票 Webhook 受信のシミュレーション（デモ）。本物と同じ形のペイロード（`{event, payload:{issueId}}`）を受け、受信後の処理（Issue 取得→ピン保存→照合）を本物の受け口と同じ経路で実行する |
| `POST /api/sim/webhook/hg` | 管理用: 対象モデルにピンされた Issue（HG では #48〜52）を一括でシミュレーション経路に流し、スナップショットを生成する（再実行可能） |

## 状態管理の設計（スナップショット方式）

このアプリは「履歴の記録者」であり、状態の管理者ではありません。現在値は常に Forma が正です。
アプリ側が持つのは `data/` の中だけです（GitHub には push しません）。

- `data/snapshots.json` — Issue ごとの前回値（status／担当者）と、変化イベントの追記型ログ。
  起動時と `POST /api/refresh` で全件取得し、前回値と比較してイベントを生成します。
  **イベントの時刻は「検出時刻」であって実際の変更時刻ではありません**（画面にも明示）。
  初回取り込みはベースライン記録のみで、イベントは発生しません。履歴は運用を続けるほど溜まります。
- `data/diff-cache/` — このアプリ自身が実 API ジョブ（Model Properties の index＋diff）で取得した
  diff 結果の正規化キャッシュ（format 3。変更行には形状シグナルに加えて「プロパティ値の実変化」
  フラグを持ち、関連ペア判定に使います）。各ファイルにジョブ実行日時（`jobRunAt`）と対象ペアを記録します。
  ここに無いペアは、初回アクセス時にジョブを実行して取得します（202 応答で状態を返し、完了後に結果を返す）。
  ファイル名には対象モデルの lineageId を含みます（`diff-<lineageId>-<from>-<to>.json`）。
  版番号だけでは、対象アイテムを切り替えたときに別アイテムの同じ版ペアの結果を誤って読むためです
  （旧アイテムの旧名キャッシュ `diff-<from>-<to>.json` は、旧アイテムを対象にした場合に限り読みます）。
- `data/captures/` — モデル更新時の自動スクショ（下記）の PNG とジョブ記録
  （`index.json`：ペア・対象要素・カメラ種別・成否・失敗理由）。スナップショットには
  既知の版一覧（`knownVersions`）も持ち、新しい版の公開検出に使います。
- `data/pin-snapshots.json` — ピン時点スナップショット（デモスライス、下記）。
  起票 Webhook の受信シミュレーションで生成され、ピン座標・ピンした版・対象要素の
  その時点の状態（bbox・geomHash・プロパティ全件）と、最新版との照合結果を持ちます。
  外部ストレージのモックとして扱います。

## モデル更新時の自動スクショ（サーバ側撮影）

新しい版の公開を refresh で検出したら、新ペア（直前版→新版）の変更箇所を、サーバ側の
ヘッドレス Chrome だけで撮影します（クライアントのブラウザは不要）。撮影ページ
（`public/capture.html`）が APS Viewer で差分ビューアと同じ見た目（色分け＋見通し確保＋
引出線ラベル）を描き、`getScreenShot` で撮影します。

- 対象: ①そのペアでアンカー要素が変化した、開いているピン付き Issue のアンカー箇所
  （最優先）。②その他 geometry 変化要素は近接クラスタ単位で上限 5 件
  （`HG_CAPTURE_MAX_CLUSTERS`、1 クラスタ最大 25 件）。
- カメラ: ①のうちピンがカメラ（viewerState）を持つ場合は**ピンカメラ再現**（ピンの
  視点・注視点・上方向をそのまま使用）。viewerState が無いピン（API 作成ピンは空、
  という実測）については**代替カメラ**（ピン位置を注視点に方位 45°・仰角 28°・距離 60）。
  ジョブ記録の `camera`（`pin`／`fallback`）で区別できます。②は計算カメラ
  （ピボット＝対象の中心、仰角 28°）。
- 結果はタイムラインのモデル更新イベントの下にサムネイル表示（クリックで拡大）し、
  成否・件数も出します。失敗した撮影は理由つきでジョブ記録に残り、refresh は壊れません。
- 前提: 撮影ホストから Autodesk の Viewer CDN と APS エンドポイントへ到達できること。
  開発 VM は CDN に到達できないため、VM ではパイプライン（検出→キュー→撮影試行→
  記録→表示）までが検証範囲で、実撮影の画は到達可能なホストでの確認事項です。
- 設定: `HG_CAPTURE_ENABLED=0` で無効化（既定は有効）。Chrome は `HG_CHROME_PATH` で
  指定でき、未指定時は Playwright の Chromium → `/opt/meta-chromium/chrome` → PATH 上の
  Chrome の順に探します。手動実行は `POST /api/captures/run`（`{from, to}`）。

将来は Issues の Webhook（`issue.updated-1.0` 等）で検出をリアルタイム化する想定で、
その場合も「前回値との比較でイベント化する」核はそのまま使えます。今回はポーリング方式です。

## diff の取得（全て実行時 API）と実測値との対応

**データは全て実行時に API から取得します。事前投入データは使いません。**
diff は、アプリが Model Properties API の index＋diff ジョブをその場で実行して取得し、
結果だけを実行時キャッシュ（`data/diff-cache/`、ジョブ実行日時つき）に保存します。

参考として、同じジョブで取得できる統計は過去の実測（`research/v2-diff-measurement.md`）と一致します:

| ペア | 追加 | 削除 | 変更 | bbox を持つ行 |
|---|---|---|---|---|
| V1 → V2 | 450 | 450 | 34,718 | 7,092 |
| V2 → V4（実質 V3） | 51 | 33 | 374 | 158 |
| V1 → V4 | 468 | 450 | 34,718 | 7,092 |

注意（実測で判明したこと）:

- **「変更」34,718 件の大半はロケールノイズ**です。英語ロケールの Revit で作られたモデルを
  日本語ロケールで再保存すると、パラメータ名等の表記差でほぼ全要素が「変更」になります。
  日本語保存同士の V2→V4 では変更は 374 件まで減りました。実際に形が変わった目安は、
  形状ハッシュ変化・bbox 移動のある「形状シグナル」の件数です（画面でも併記）。
- **旧アイテムでは V3 は登録ファイルが破損しており変換できません**（内容の実体は V4）。
  そのため旧アイテムの V4 のモデル更新イベントの diff は V2→V4 ペアで表示します。
  現行の対象である HG アイテムにこの事情はありません（V1→V2→V3 の順で正常に公開されています）。
  HG の V1 は対照ファイル（日本語再保存）のため、HG の V1→V2 は日本語保存同士のペアとなり、
  変更件数は旧アイテム V1→V2 のようなロケールノイズの洪水にはなりません
  （同じ内容ペアの実測: 追加34／削除34／変更267、`research/v2-diff-measurement.md` §8）。
- ピン近傍の絞り込み: Issues API のピン座標は Viewer 座標系、diff の bbox は Revit 共有座標系で、
  しかもピンは要素上の一点（中心ではない）ため、座標同士を直接は比較できません。
  本アプリでは「ピン対象要素の bbox 中心（共有座標系）」をアンカーに、水平 30ft 以内・
  上下 ±6ft の行を数えます（viewer-mock と同じ基準）。対象要素がそのペアの diff に
  現れない場合は、このアプリが取得済みの他のペアの diff の bbox で代用し、それも無い場合は
  ファイル全体の件数のみ返してその旨を明示します。近傍判定はヒューリスティクスであり、
  「その Issue の修正」とは限りません。

## 既知の制約

- **対象プロジェクト（Snowdon Towers）の実 Issue は、当初コメントが全件 0 件**でした
  （Forma の画面からコメントが付いた Issue はまだありません）。そのため実データのタイムラインは
  起票・モデル更新・スナップショットで検出した変化イベントが主になります。
  API 経由で投稿したコメント（旧 #43〜47、新 #48〜52）も自動的にタイムラインに表示されます。
- ピン時点のサムネイル（`snapshotUrn`）が取得できるのは実 Issue のうち 3 件のみです
  （2026-11-17 時点。Forma の画面から作られた Issue だけが画像を持ちます）。無い Issue では表示を省略します。
- APS Viewer の描画は、Viewer の CDN に到達できる環境（実機ブラウザ）でのみ確認できます。

## ピン時点スナップショットと Close 検証（デモスライス）

このアプリはデモであり、実現可能性を実データで通しで見せることが目的です。その一環として、
「起票時にピンが指した要素の状態を保存し、Close 時に最新版と照合する」流れを実装しています
（仕様は SPEC §7.9）。

- **Webhook はシミュレーション**です。本物の Webhook は登録しておらず、公開受け口もありません。
  `POST /api/sim/webhook` が本物と同じ形のペイロードを受け、受信後の処理
  （Issue を API で GET → ピン抽出 → ピン時点の要素状態を保存 → 最新版と照合）は
  本物の受け口と同じ経路を通します。Issue 詳細の「ピン時点スナップショット」パネルにも
  その旨を明示しています。
- ピン時点の状態は、ピンした版（Issue 作成以前に公開された最新の版）の Model Properties
  インデックス実データから復元します（ピン座標・要素名・カテゴリ・bbox・geomHash・プロパティ全件）。
- 照合の判定は「対象要素が削除（解消方向の変化）／変化あり（形状・移動・プロパティの要約つき）／
  変化なし」で、Issue 詳細のパネルと、Closed な Issue のタイムラインの Close イベントに表示します。
- HG の実データでの実測（V1 ピン時点 × V3 照合）: #48 テラス床＝変化なし、#49 藤棚＝要素削除、
  #50 外灯＝移動（Δx −1.671, Δy +3.424, Δz 0）、#51 ドア＝プロパティ（コメント None → diff-test）、
  #52 壁＝移動（Δx +0.14, Δy +0.068, Δz 0。In Review のため現時点比較）。
