## 1. 背景と目的

### 1.1 業務の流れ（このアプリが支援する仕事）

指摘事項の確認と是正は、次の循環で進む業務である。

1. レビュイーが指摘事項を迅速に確認する。
2. 担当者が指摘を受けてモデルを修正し、モデルのバージョンが上がる。
3. 修正の結果を、更新されたモデル上で迅速に確認する。
4. レビュアーへ返答し、Issue を close まで進める。

### 1.2 既存の Forma Issues の課題

- 指摘事項を一覧で見ることはできるが、**モデル上のどこが指摘対象なのかは、ピンした時のサムネイル（スナップショット）でしか確認できない**。
- **モデルのバージョンが上がった時に、そのモデルの状態を Issue 上では確認できない**。修正結果を確認するには、都度モデルを見に行かなければいけない。

### 1.3 このアプリの目的

上記の課題を**一つの画面上で完結**させ、かつ**一つ一つのステップを迅速に行える**ようにすることで、レビュイーの確認から、担当者による修正、更新されたモデルでの結果確認、レビュアーへの返答、Issue の close までの業務の円滑化を助ける。

この目的が、以降の仕様の判断基準になる。たとえば、要素情報の自動付与（モデルを開かずに Issue 側で位置が分かること）、3D 表示と手前の部材の透明化（サムネイルではなく実モデル上で対象を確認できること）、一覧の高速化や読み込み前の先行表示（各ステップの待ちを削ること）は、いずれもこの目的から来ている。

### 1.4 機能概要

Forma（Autodesk Construction Cloud、以下 ACC）の実 Issue を Issues API で取得し、Issue のピンが指すモデル要素の情報（階・位置・タイプ名・材質など）を自動で付与して一覧表示するデモ。あわせて、ピン先の要素を 3D ビューア（APS Viewer）で表示し、「建物の奥にある部材や、部材と部材の間にある部材を見えるようにする」ための表示機能を持つ。

主な機能：

1. **Issue 一覧**：Forma の Issue 項目に加え、モデルから読んだ要素プロパティが自動で列として追加される。列の表示/非表示はユーザーが設定可能。検索・ステータス絞り込み・並び替え・列ヘッダソート・ページング対応。
2. **Issue 詳細と編集**：スナップショット画像、自動付与された要素情報の一覧を表示。タイトル／ステータス／期日／説明を編集し、Issues API（PATCH）で実 Issue に保存できる。
3. **3D 表示（APS Viewer）**：Issue のピン先に応じてモデルを自動で切り替える。単独フォーカス表示と、モデル上に全 Issue を表示する「一覧モード」（既定 ON）の2形態。
4. **手前の部材の透明化**：選択中の Issue の対象要素について、カメラと対象の間にある部材だけをゴースト表示（フレームのみ表示）にして見通しを確保する。
5. **OBJ 表示モード**：対象要素＋周辺要素を OBJ で切り出して軽量ビューア（three.js）で表示する切り替え機能。
6. **バージョン間 Diff による変更表示（v8.33）**：ピン時点のモデルバージョンと最新バージョンを Model Properties API の Diff で比べ、対象要素の変更（追加／削除／形状・移動・プロパティの実質変化）を Issue の表と詳細に表示する。比較ペアは「ピン時点 → 最新」に固定（ユーザー決定）。

### 1.5 既存手段との関係（差別化の前提）

- Autodesk 純正の **Revit Issues アドイン**が既に存在する。Revit の中で ACC の Issue を開き、対応する要素のハイライト、保存されたビューの再現、Issue の編集・コメント・ステータス変更・解決まで行えるもので、2020 年に BIM 360 向けとして公開され、現行も Revit の新バージョン向けに提供が続いている。
  - 出典：[Revit Issue Add-in リリースノート（2020-12-14）](https://blogs.autodesk.com/bim360-release-notes/2020/12/14/%F0%9F%86%95-revit-issue-add-in-december-14th-2020/)、[Issues Addin for Revit 2024 v6.0.0 リリースノート](https://up1.autodesk.com/2024/RVT/RIA_6.0.0_ReleaseNotes_Revit2024.htm)
- 本アプリは、このアドイン（および Forma Issues の標準機能）との**差別化が成立することを前提**とする。差別化が崩れる場合は、アプリの存在意義自体を再検討する。
- 差別化の具体的な比較（現状でどこがどう違うか）は変動が大きく更新の負担になるため、本書には記載しない（2026-11-16 ユーザー指示）。

### 1.6 目指す世界（将来像・未実装）：履歴グラフで「同じ指摘」を追う

> 追記（2026-11-17）：この将来像は、今のビューアアプリ（sample-d）とは**分けて別アプリとして検討する**ことになった（ユーザー決定）。詳細は別チャット「履歴グラフ（同じ指摘の追跡）」で育てる。ここには経緯として残す。

- 背景：現状の Forma では、Issue について比べられるのは起票時のサムネイルと現行モデルの実態だけであり、変更履歴を見て任意のモデル差分を比べることができない。
- 実際の運用ではモデルは何度も更新され、その間に Issue の関係者は設計者・監理者・施主・施工者と変わっていく。その間、実は同じ指摘が繰り返し出ていることが起こっている。履歴を確認できれば、最適なアクション（再指摘ではなくエスカレーション、重複の統合、根本原因の追及）を取れる。
- UI は**履歴グラフ**とする：縦軸にファイルのバージョン、その間に Issue の起票・コメント・ステータス変更をぶら下げ、バージョン間には差分の要約を示す。Forma にはない形であり、差別化の一つになる。
- ステータス変更などの活動履歴は API で取得できないため、この機能では**アプリ側がスナップショットを履歴として保持してよい**（ユーザー決定。§2 の前提に対する、この機能限りの例外）。
- 要素の同一性：ピン先の要素 ID を第一のキーとする。ただしモデル更新で要素が削除→再作成されると ID は変わる（例：四角い窓を消して丸窓に作り替える）。その場合は、ピン座標（ワールド座標。要素が消えても指摘の場所は残る）、階、ホスト要素、カテゴリ等の近さから「作り替え候補」を提示し、人が「同じ」と確定して履歴をつなぐ。git の rename detection と同じ発想で、自動では確定しない。

## 2. 前提と設計原則

- **アーキテクチャ前提（ユーザー指定、2026-11-16）**：サーバー側では事前にどのモデル・部材があるかを把握しておきたくない。サーバーはあくまで Forma（APS）を呼び出すだけとし、データの状態管理は Forma 側に置く。
  - ただし現行実装には、この前提に対する**例外が1つ残っている**：要素情報の付与に使う「要素索引」（§5.4）をサーバーが構築・キャッシュしている。索引は登録簿（§4）のモデルについてのみ、起動後に API から動的に構築するもので、事前の手作業による生成物ではない。読み込み前の先行表示（§6.6）は索引を使わず、この前提どおりに実装されている。索引を廃して付与も動的取得へ寄せるかどうかは未決（ユーザーの判断待ち）。
- **ピン座標の座標系**：Issue ピン（`linkedDocuments.details.position`）は **Viewer のワールド座標**そのものである（2026-11-16 に実測で確定。変換式は「ワールド = SVF ローカル − globalOffset」）。公式ドキュメントに座標系の明記はない。
- **Issue のピンは空間ではなく必ずオブジェクトに対して付く**ものとして扱う（デモの割り切りとしてユーザー承認済み）。
- 対象 Issue の特定は、ピンの `externalId` → モデル索引の対応表 → Viewer の `dbId` の順で行う。Model Derivative の `objectid` と Viewer の `dbId` は一致しないため、この読み替えが必須。

## 5. サーバー仕様（server.mjs）

### 5.1 起動シーケンス

1. `.env` と `data/models.json` と `.token.json` を読み込む。
2. `cache/index-{key}.json` があれば索引を即座に読み込み、そのモデルは `ready` として扱う。
3. HTTP サーバーを即座に起動する（索引の完成は待たない）。
4. 索引の非同期構築を開始する（`initIndexes`）。キャッシュ使用中のモデルはモデルの現行バージョンを確認し、バージョンが変わっていたら作り直す。
5. Issue 一覧の先回り取得（warm-up）を開始する（§5.6）。

### 5.2 認証

- **2-legged（アプリ認証）**：スコープ `viewables:read data:read`。トークンはサーバー内でキャッシュし、有効期限の5分前に失効扱いにして再取得する。Viewer 用トークンの配布（`/api/token`）と、プロパティ取得・サムネイル・バージョン確認に使う。
- **OBJ ジョブ用 2-legged**：変換ジョブ投入には広いスコープ（`data:read data:write data:create viewables:read`）が要るため、別トークンを取得・キャッシュする。
- **3-legged（ユーザー認証）**：Issues API と Admin API とスナップショット取得に使う。refresh token は `.token.json` に保持し、**ローテーションに必ず追随してファイルへ書き戻す**（書き戻さないとチェーン全体が失効し、再ログインが必要になる）。access token の取得から45分以内は再利用し、それを超えたら refresh する。サーバーは起動時に `.token.json` を読み込むため、外部でトークンを更新したらサーバーの再起動が必要。

### 5.3 API エンドポイント

| メソッド・パス | 仕様 |
|---|---|
| GET `/api/token` | Viewer 用 2-legged トークンを返す（`access_token` と残り秒数 `expires_in`、最小60秒） |
| GET `/api/issues` | 実 Issue の取得＋要素情報の付与（§5.5）。応答は `{ models: [{key, name, short, version, urn, guid, indexStatus}], issues: [...], fetchedAt }`。一覧キャッシュの仕様は §5.6 |
| GET `/api/index-status` | 索引の構築状態だけを返す軽いエンドポイント `{ models: [{key, short, indexStatus}] }`（画面のポーリング用） |
| POST `/api/issues/update` | 実 Issue の PATCH 中継。ボディ `{ id, patch }`。patch のうち **title / description / status / dueDate の4項目だけ**をホワイトリストで通す。成功したら一覧キャッシュを即座に破棄する |
| GET `/api/thumbnail?model={key}` | モデルのサムネイル画像（PNG）。メモリキャッシュ。`Cache-Control: max-age=3600` |
| GET `/api/snapshot?urn={snapshotUrn}` | Issue のスナップショット画像。`urn:adsk.objects:os.object:` で始まる URN のみ受理。署名付き S3 URL 経由で取得（§5.7）。メモリキャッシュ。`Cache-Control: max-age=3600` |
| GET `/api/extract?issue={Issue ID}` | 対象要素＋周辺の OBJ 抽出（§5.8）。応答は `{ modelKey, targetDbId, neighborCount, included: [{dbId, name, target}], obj }`。対象要素がない Issue は 404、索引が未完成なら 409 |
| その他 | `public/` 配下の静的ファイルを配信（`/` は `index.html`）。パストラバーサルは拒否 |

エラー時はいずれも JSON `{ error }` を返す（API 系は 502、個別の事情は上記のステータス）。

### 5.4 要素索引（モデル情報）

要素情報の付与に使う対応表とプロパティ集。モデルごとに構築する。

- **構築手順**：
  1. Model Derivative のプロパティ一式を取得（`GET /modelderivative/v2/designdata/{derivativeUrn}/metadata/{viewableGuid}/properties?forceget=true`。202 の間は3秒間隔でポーリング、最大120回）。平坦化して `externalId → プロパティ` の表にする（キー名が `_` で始まるものは除外。要素名から Revit の要素 ID `[数値]` も抽出）。
  2. 変換データ同梱のプロパティ DB `model.sdb` を manifest 経由でダウンロードし、`_objects_id` テーブルから `externalId → dbId` の対応表を作る（`node:sqlite` で解析）。
- **状態**：`idle`（未着手）／`building`（構築中）／`ready`（完成）／`error`（失敗、理由を保持）。状態は `/api/issues` の `models[].indexStatus` と `/api/index-status` で公開する。
- **キャッシュ**：完成したら `cache/index-{key}.json`（versionId・viewableGuid・構築日時・2つの表）へ保存し、次回起動時は即座に使う。起動時にモデルの現行バージョン（Data Management の versions 先頭）とキャッシュの versionId を比べ、変わっていたら作り直す（バージョン確認結果は60秒キャッシュ）。**viewableGuid がキャッシュと異なる場合も作り直す**（v8.34。プロパティの取得元 viewable を変えた時に古い表が残るのを防ぐ）。
- **実測**：コールドスタートからの構築は1モデルあたり約3〜6秒、全モデル ready まで約6秒。
- 索引が `ready` でないモデルの Issue は、要素情報なし（`element: null`、`targetDbId: null`）で返す。

### 5.5 Issue の取得と付与（enrich）

- 取得：`GET /construction/issues/v1/projects/{PID}/issues` を limit 50 でページング（最大200件）。`deleted` の Issue は除外する。
- 付随情報の解決（どちらも10分 TTL キャッシュ、取得は並行）：
  - Issue タイプ：`GET .../issue-types?include=subtypes` で subtype ID → {タイプ名、subtype 名、コード}。**コードは Forma 画面のチップ文字と一致する**（例：Observation > Quality → `OQ`）。
  - メンバー：`GET /construction/admin/v1/projects/{projectId}/users`（limit 200）で autodeskId → 表示名。メールアドレスは画面に出さない。
- 画面へ返す Issue オブジェクトの主なフィールド：`id`、`displayId`、`title`、`description`、`status`、`dueDate`、`startDate`、`assignedTo`／`assignedToName`、`watcherNames`、`published`、`typeLabel`（「タイプ > subtype」）、`typeCode`、`createdAt`、`openedBy`／`openedAt`、`createdBy`、`snapshotUrn`、`snapshotHasMarkups`、`permittedStatuses`、`customAttributes`、`attachmentCount`、`commentCount`。
- ピンと要素の解決：`pin = { modelUrn, viewName, objectId, externalId, position, createdAtVersion }`（linkedDocuments の先頭から。`createdAtVersion` はピンが置かれた時点のモデルバージョン）。modelUrn が登録簿の lineage と一致するモデルを `modelKey` とし、索引が ready なら externalId から `targetDbId` と `element`（プロパティ一式）を付与する。
- バージョン間 Diff の結果（§5.9）があれば、`changeState`（`na`／`building`／`ready`／`failed`）と `change`（ペアの版番号、対象要素の変更種別とシグナル、ペア全体の件数）を付与する。索引の有無とは独立に判定する。

### 5.6 Issue 一覧の短期キャッシュ（v8.30）

初回表示の待ちを削るための仕組み。

- 取得済み一覧を **30秒** 使い回す。期限切れ後は手元の一覧を即座に返し、裏で取り直す（stale-while-revalidate）。取得は同時に1本だけ。
- サーバー起動時に先回り取得（warm-up）する。
- 編集（`/api/issues/update`）が成功したらキャッシュを即座に破棄する。
- **索引の構築中はキャッシュしない**（付与内容が変わるため、従来どおりライブ取得する）。バージョン間 Diff（§5.9）の取得中も同様にキャッシュしない。
- 実測：変更前は冷えた初回 約2.75秒／温まった2回目 約0.23秒 → 変更後は定常時・TTL 切れ直後とも約2ミリ秒。

### 5.7 画像の取得

- **モデルサムネイル**：Model Derivative の thumbnail エンドポイントから取得し、メモリにキャッシュする。
- **Issue スナップショット**：Issue の `snapshotUrn`（Forma が起票時に撮ったピン視点の画像）が指す OSS オブジェクトを、旧来の OSS 直 GET（廃止済みで 403）ではなく、`GET /oss/v2/buckets/{bucket}/objects/{object}/signeds3download`（3-legged）で署名付き S3 URL（有効期限 約2分）を得てから取得する。メモリにキャッシュする。
- **API 経由でスナップショットを新規生成することはできない**（Forma 画面で人が起票した時にだけ生成される）。API 起票の Issue は `snapshotUrn` が null。

### 5.8 OBJ 抽出（/api/extract）

- 対象要素の `objectid` に周辺要素の `objectid` を加え、Model Derivative の OBJ 変換ジョブ（`POST /modelderivative/v2/designdata/job`、URN はボディに入れる。`advanced: { modelGuid, objectIds, exportFileStructure: 'single' }`）で切り出す。
- **周辺要素の選定（簡易版、最大48件）**：対象の通り芯（Column Location Mark）を解析し、①隣接する通り芯（同じ記号で番号±1、または同じ番号で記号±1）を持つ要素を最優先、②同じ階（Level／Reference Level／Base Level／Base Constraint／Top Level のいずれか）かつ同タイプ、③同じ階のみ、の順で補う。
- manifest を5秒間隔でポーリング（最大48回）し、得られた OBJ のグループ名（`g Obj.{dbId}`）で**内容照合**する（対象 dbId を含み、全グループが要求集合に含まれ、要求の半数以上が揃っていること）。過去のジョブの成果物との取り違えを防ぐため。
- 結果は要素集合単位（モデル key＋objectIds のハッシュ）で `cache/extract-{hash}.json` にディスクキャッシュする。
- **対応状況（実測）**：Snowdon 3モデルは成功。**DACH と sample_architecture は OBJ 変換自体が「No Geometries to extract」で失敗する**（ファイル固有の問題）。その場合は画面にエラーを表示する。

### 5.9 バージョン間 Diff（v8.33、Model Properties API）

ピン時点のモデルバージョンから最新バージョンの間に、Issue の対象要素がどう変わったかを表示するための仕組み。

- **比較ペア**：Issue ごとに「ピン時点の版（`pin.createdAtVersion`）→ そのモデルの最新版」に固定する（ユーザー決定 2026-11-17。任意ペアの選択はしない）。ピン時点と最新が同じ版の Issue、ピンなし・対象外モデルの Issue は比較対象なし（`changeState: 'na'`）。
- **取得フロー**（3-legged）：Model Properties API（`construction/index/v2`）で ①両版の索引を `indexes:batch-status` で確保し FINISHED までポーリング、②`diffs:batch-status` で Diff ジョブを作り FINISHED までポーリング、③`fields` と、全行を SVF2Id 範囲（2,000 件刻み）のクエリで取得する。ペア単位で非同期に実行し、ジョブは直列に1本ずつ流す。必要なペアは Issue の取得時に自動で洗い出して開始する（`planDiffs`）。
- **判定（ロケールノイズの除外）**：ロケール差異でフィールドキーが付け替わると、無変更の要素でも大量に「変更」として現れる（実測：Snowdon 建築 V1→V5 で生の変更 34,719 件）。そのため対象要素の変更は次のシグナルで判定し、どれも無ければ「実質的な変更なし」とする：追加（OBJECT_ADDED）／削除（OBJECT_REMOVED）／形状ハッシュ（geomHash）の変化／bbox の純平行移動（移動距離はフィート→メートル換算で併記）／プロパティ値の実質変化（同一キーで両側とも非 null の異なる値、または新版側の ASCII 文字列・数値が旧版側の値集合に存在しないこと。履歴グラフ側と同一基準）。
- **保持する結果**：追加・削除の全要素と、シグナルのある変更要素だけを要素単位で保持する（見かけ上の変更要素は保持しない）。あわせてペア全体の件数（追加／削除／実質変更／生の変更）を保持する。結果は `cache/diff-{key}-v{from}-v{to}.json` に保存し、再起動後はそれを読む。
- **状態の公開**：`/api/issues` と `/api/index-status` の各モデルに `diffStatus`（`na`／`building`／`ready`／`failed`）を含める。画面は構築中バナーの対象に含め、完了時に一覧を取り直す。
- **実測（2026-11-17）**：Snowdon 建築（V5 まで）の3ペア（V1→V5、V2→V5、V4→V5）が取得できた。所要は索引が既存のペアで約20秒、索引の新規構築を含むペアで約140秒。検証用 Issue の判定：#43 植栽＝削除（V2 で追加された要素が最新では消えている）、#44 藤棚＝変更なし（最新では戻っている）、#45 外灯＝形状変更＋移動 約1.16m、#46 ドア＝プロパティ変更、#47 壁＝形状変更＋移動 約0.05m。

## 6. クライアント仕様（public/）

### 6.1 画面レイアウト（v8.22／v8.23）

- 画面全体は縦方向 flex。見出し1行の下に2カラム構成。
- **左カラム**：上＝Issue 表パネル、下＝ビューアパネル。
  - 表パネルは**表示件数に応じた高さ**（中身ぴったり）になり、残りをビューアが使う。件数が多い場合は表が伸びるが、ビューアの最小高さ **220px** を確保し、表の超過分はパネル内スクロールになる（ヘッダは sticky で固定）。
- **右カラム**：Issue 詳細パネル（幅 350px、画面の**全高**、内部スクロール）。Issue を選択した時だけ表示される。表示・非表示でビューア幅が変わるため、切替後に `viewer.resize()` を呼ぶ。
- データ到着前は Issue 表にスケルトン UI を表示する。

### 6.2 Issue 表

- **列定義**：固定列17件＋自動列。
  - 固定列（グループ「Issue」）：Title／Status／Type／Assigned to／Due date／Start date／Placement（モデルファイル名＋バージョンのピル表示）／ID／作成日／公開／コメント（件数）／添付（件数）。
  - 固定列（グループ「モデル情報」）：対象要素（要素名＋Revit ID。ピンなしは「ピンなし」、対象外モデルは「対象外モデルのピン」）／モデル／階（Level 系キーの優先順で解決）／位置（Column Location Mark → Mark → Type Mark の順）／**変更（v8.33）**：バージョン間 Diff（§5.9）の判定を色ドット＋ラベルで表示する（変更あり 橙／削除 赤／追加 緑／変更なし 灰／取得中 青／取得失敗 赤）。比較対象がない Issue は「—」。
  - 自動列（グループ「モデル情報（自動）」）：全 Issue の要素プロパティに実在するキーを出現頻度順に列化する（`name`／`revitId`／`objectid` は除く）。ラベルは日本語対応表（タイプ名・階・位置（通り芯）・材質・構造用途・カテゴリ・長さ・面積・体積など）で表示し、対応表にないキーは英語名のまま。
  - 自動列（グループ「カスタム属性」）：Issue の customAttributes のタイトルを列化する。
- **既定の表示列**：Title／Status／Type／Assigned to／Due date／Start date／Placement／変更 の8列（v8.33 で「変更」を追加。既存ユーザーの保存済み列設定にも一度だけ自動でマージされる）。
- **列の設定**：ツールバーの「列の設定」からチェックボックスで切り替える。列名の絞り込み入力付き。選択は localStorage に保存される（§6.10）。
- **ステータス表示**：色バー＋英語ラベル（Draft 灰／Open 橙／Pending 濃橙／In review 青／Closed 緑／Void 灰）。Type 列はコードの丸チップ＋「タイプ > subtype」。担当者未設定は「Unspecified」。
- **Title セル**：左側に **3D ボタン（48×29px）** を置く（対象要素がある Issue のみ。ない場合は同じ幅の空白）。行クリックは詳細を開くだけで、ビューア表示はしない（§6.5）。
- **検索**：タイトル・説明・要素名・モデル名・番号を対象に部分一致（入力のたびに1ページ目へ）。
- **ステータス絞り込み**：ドロップダウン（データに実在するステータスだけを選択肢にする）。
- **並び替え（2系統）**：
  - ドロップダウン：番号↑／番号↓／期日↑／期日↓／タイトル順。
  - **列ヘッダクリック（v8.18）**：クリックのたびに 昇順（▲）→ 降順（▼）→ 解除（ドロップダウンの並びに戻る）。数値・日付・文字列（日本語、数値混じり対応）で比較し、**空値は昇順・降順どちらでも常に最後**。ドロップダウンを変えると列ソートは解除される。状態は localStorage に保存される。
- **ページング**：前へ／次へ＋「n / m ページ（全 N 件）」。表示件数は 5／10／25／50／100 から選択（**既定 5**、localStorage に保存）。

### 6.3 詳細パネル

- 見出しは「Issue #番号」。項目：サムネイル画像／Title（編集可）／Status（編集可）／Type（チップ表示）／Due date（編集可）／Description（編集可）／Assigned to（名前）／Watchers（名前の列挙）／Placement（モデル名＋バージョン）／対象要素（自動付与されたプロパティの定義リスト。日本語ラベル付き、`revitId` と `objectid` は出さない）。
- **モデル更新による変更（v8.33）**：対象要素の下に専用の節を持つ。内容は「V{ピン時点} → V{最新}：判定文」（対象要素は最新版で追加された要素です／最新版では削除されています／変更があります／実質的な変更はありません）＋シグナル（形状の変更／移動（約 X m）／プロパティの変更）＋実質変化したプロパティの「名前：旧値 → 新値」一覧（最大12件）＋ペア全体の件数（追加・削除・実質変更。見かけ上の変更の件数は判定から除外した旨を併記）。取得中は「変更情報を取得中…（Vx → Vy）」、失敗時はその旨、比較対象がない場合は「比較対象なし（ピン時点と最新が同じバージョンです）」と表示する。
- **サムネイルの優先順位**：① Forma のスナップショット（`snapshotUrn`）→ ② 読み込み失敗時の代替としてモデルサムネイル。スナップショットがない Issue は ③ ビューアのキャプチャ（§6.5、表示済みの場合）→ ④ モデルサムネイル。
- **編集と保存**：「変更を保存」で `/api/issues/update` に送り、実 Issue へ PATCH する。保存後は一覧を取り直し、「保存しました（Forma 側に反映済み）」を表示する。失敗時は理由を表示する。
- **ステータスの選択肢**は Issue ごとの `permittedStatuses`（Forma が許可する遷移）に従う。取得できない場合は全ステータス（draft／open／pending／in_review／closed／void）を選択肢にし、現在のステータスは必ず含める。
- 「ビューアで表示」ボタンは §6.5 の 3D 表示と同じ動作（対象要素がない Issue では無効）。

### 6.4 ビューア共通

- Viewer は APS Viewer（GuiViewer3D）。モデルは SVF の逐次配信で読み込む（遅延読み込み）。読み込むビューは既定ジオメトリ任せにせず、`data/models.json` の viewableGuid で指定した viewable を明示的に開く（v8.34。Snowdon 建築の既定は壁だけの viewable で、全カテゴリが表示されなかった）。viewableGuid はグラフィックスリソース（SVF）の GUID で geometry ノード自身の GUID とは別物のため、選択は「配下にその GUID のリソースを含む geometry ノード」を探して行う（`findByGuid` が返すリソースノードを直接開くと Viewer が未対応エラーになる）。見つからない場合のみ既定ジオメトリにフォールバックする。
- **ピン座標の座標系（v8.34）**：Forma 画面で起票されたピンは Viewer のワールド座標。一方、API 起票のピン（スナップショットなし）には SVF2 側の座標系（Revit 内部座標 − refPoint）で記録されたものがある（履歴グラフ実験の #43〜47 で実測）。対象要素が表示モデル内に解決できる場合は読み込み完了後に要素ボックスへ付け直すため影響しない。解決できない場合に限り、モデルに pinFrame（実測した変換：world ＝ affine・(pin ＋ refPoint)、シーン座標 ＝ world − globalOffset）があれば変換して先行表示する。変換は snowdonarch のみ（他モデルは対象ピンなし）。
- **初期化シーケンス（v8.28）**：Viewer の初期化と `/api/issues` の取得は並行するが、**データが届く前に初期化だけ終わった場合はモデルを読み始めない**。データ到着側の初期処理が、選択中の Issue のモデルで読み込みを開始する（先頭モデルで読み始めて切り替える二重読み込みの防止）。
- **初期選択**：データ到着時、対象要素を持つ先頭の Issue を選択して詳細だけを開く（ビューア表示はしない）。ビューアの初期モデルはその Issue のモデル。
- **読み込み表示**：ビューア上部のピル型表示で実状態を出す（データ読み込み中 → モデル読み込み中（進捗％）→ 完了で消える）。入力は塞がない。ステータス欄（ビューア下）にも進捗・結果・件数などの文言を出す。
- モデルの切り替えは Issue の選択・3D 表示に連動して自動で行う（`ensureViewerModel`）。
- Viewer の CDN に到達できない環境では、その旨を読み込み表示とステータス欄に出す。

### 6.5 単独フォーカス表示（3D ボタン）

- 起動経路：表の行の 3D ボタン、または詳細の「ビューアで表示」。OBJ モード時は OBJ 表示に切り替わる（§6.9）。
- **対象の強調**：対象要素を濃い赤で theming（一度だけ塗る。色替えの点滅は再描画負荷が高いため使わない）。位置の合図は画面上の CSS ピン（波紋アニメーション、3D 描画に触らない）。
- **フォーカスピンの表示条件**：ルート読み込み後から表示する。読み込み中はピン座標をアンカーに先行表示し、形状の読み込み完了後は部材ボックスの中心に合わせる。対象がカメラの後ろにある場合と、完了後に対象が非表示の場合は出さない。一覧モード中は出さない。
- **カメラのフィット**：
  - 形状の読み込み完了後、（モデル：Issue）の組み合わせごとに**1回だけ**フィットする。明示操作（3D ボタン／ツールバーのフォーカスボタン）の場合はやり直す。
  - フィット位置は標準の fitToView ではなく、部材ボックスから距離を計算する「引き」の構図（半径 ÷ tan(fov/2) × **1.9**）。
  - 方向は現在の**方位だけを引き継ぎ、仰角は 28° に固定**。上方向は常にワールド Z。回転中心（ピボット）は対象の中心に合わせる。
  - 移動は easeInOutCubic の補間アニメーション（所要時間は移動距離に応じて **0.65〜1.2秒**）。移動中にユーザーがビューアを操作（pointerdown／wheel）したら即座に中断して譲る。OS の「視差効果を減らす」設定時、または移動距離がごく小さい場合は瞬間移動。
- **キャプチャ**：フィット後 約0.9秒でビューアをキャプチャ（560×350）し、その Issue のサムネイル代替としてメモリに保持する（API ではスナップショットを生成できないため）。

### 6.6 一覧モード（指摘事項一覧をモデルに表示）

- **既定 ON**。ツールバーの一覧ボタンで ON/OFF を切り替える。モデル読み込み完了と同時に一覧モードに入る。
- 表示内容：表示中モデルの全 Issue 要素を**ステータス色で theming** し、各要素にタイトルラベル＋引き出し線（線の先端にステータス色のドット）を表示する。選択中の Issue は要素・ラベル・引き出し線とも赤で強調する。

  | ステータス | 色 |
  |---|---|
  | open | 橙 |
  | in_review | 青 |
  | closed | 緑 |
  | pending | 紫（表の色と区別するため） |
  | draft / void | 灰 |

- **先行表示（v8.31）**：モデルのルート読み込みが済んだ時点で、ピン座標をアンカーにラベル＋引き出し線を先行表示する（索引は使わない）。形状のストリーミング中も視点変化に追随する。読み込み完了後はマーカーを作り直し、線の先を部材ボックスの中心に合わせ直す。
- **ラベルの表示条件**：指摘箇所（部材中心、またはボックスの隅のいずれか）がカメラの前にあり、かつその投影点が画面内にある場合だけ表示する。要素の非表示状態では判定しない。
- **ラベル配置（v8.15、ユーザー仕様）**：ラベルは対象の直上には置かず、画面中央の「青エリア」（左右 12.5%・上 18%・下 26% の内側）の**外側＝画面周囲のマージン帯**に散らす。
  - 中心点は動的：X は画面中央固定、Y は表示中の指摘箇所の 2D 座標の重心。
  - 中心点から指摘箇所を通る放射線が青エリアの境界を出る位置にラベルを置き、引き出し線で結ぶ。
  - **ラベル同士は絶対に重ねない**：同じ辺のラベルは辺方向にずらして最小間隔（6px）を保つ詰め込みを行い、間隔の維持を画面端への収まりより優先する。辺をまたぐ隅の衝突も全体チェックで逃がす。
  - ラベルサイズは構築時に測って保持し、配置の書き換えは transform のみ（レイアウトを引く読み取りをカメラ移動のたびに行わない）。更新は描画フレーム単位に間引く（rAF 合体）。
- ラベルをクリックすると、その Issue の詳細が開き、強調と手前の透明化が追随する。
- **3D ボタンとの関係（v8.32）**：一覧モードが ON の間は、3D ボタンを押しても**一覧モードは解除されない**。その Issue にカメラを寄せ、ラベル・引き出し線は残し、選択中の強調と手前の透明化を追随させる。読み込み中・モデル切替中に押した場合は、読み込み完了の時点で自動的にカメラを寄せる。一覧モード OFF のときの 3D ボタンは単独フォーカス表示（§6.5）。一覧モードを切るのはツールバーの一覧ボタンだけ。

### 6.7 対象の手前の部材を透明にする（ゴースト表示）

- **目的（ユーザー定義）**：建物の奥にある部材や、部材と部材の間にある部材を見えるようにすること。全体を薄くする方式ではなく、**カメラと対象の間にある部材だけ**を対象にする。
- **表示方式**：Viewer 標準のゴースト表示（`viewer.setGhosting(true)`）を有効にしたうえで、対象部材を `hide()` する。hide した部材は完全には消えず、フレーム（輪郭）だけを残して透けて見える。材質には一切触らない。
- **判定アルゴリズム**：カメラ位置から「対象ボックスを拡大した8隅＋中心」への9本の線分（スラブ法でボックス交差判定）と交わる要素を「手前」とみなす。候補は「自身のフラグメントを持つノード」のボックス一覧で、モデル単位でキャッシュする（形状確定時に作り直す）。
- **消さないもの**：対象自身、その祖先と子孫、表示中モデルの他の Issue 要素とその祖先。
- **スライダ「対象の手前を消す範囲」**：対象ボックスの拡大率を決める。拡大率 = 1 + (値/100)×2（50%→2倍、100%→3倍）。**0% でオフ。既定 50%**。値は localStorage に保存される。パネルはツールバーのゴーストボタンで開閉する。
- **静的化（v8.29、ユーザーが「付け替えをやめる案」を選択）**：透明セットは **Issue を選んだ時点のフォーカス視点で1回だけ計算して固定**し、カメラを動かしても再計算しない。再計算するのは ①Issue の切替 ②範囲スライダの変更 ③モデルの読み込み完了 の時だけ。フォーカス移動（グライド）中は適用を保留し、到着時に1回だけ適用する。ユーザーが移動を中断した場合も、その視点で1回だけ適用する。
  - 代償（仕様として明記）：大きく回り込むと透明の「窓」が視点とずれる。その場合はスライダを動かすと、その視点で計算し直す。
- **差分適用**：非表示セットの付け替えは差分だけを適用する（変わらない再計算では Viewer を一切触らない）。
- ステータス欄に「手前の部材 N 件を透明にしています」と件数を表示する（切り分け用）。
- エッジ（部材の輪郭線）は逐次配信中だけ切る（描画負荷の軽減）。

### 6.8 Viewer ツールバー拡張

Viewer のツールバーに自前のボタン群（DemoToolbarExtension）を追加する。

| ボタン | 動作 |
|---|---|
| 対象要素にフォーカス | 選択中（またはフォーカス中）の Issue の対象へ §6.5 のフィットをやり直す。一覧モード中は一覧を維持したまま寄せる |
| 指摘事項一覧をモデルに表示 | 一覧モード（§6.6）の ON/OFF。状態はボタンの見た目に反映される |
| 対象の手前を消す | §6.7 の範囲スライダパネルの開閉 |

### 6.9 OBJ モード（ビューア切り替え）

- ビューア左上の小ボタンで「APS Viewer」と「OBJ」を切り替える。選択は localStorage に保存される。
- OBJ モードでは、選択した Issue の対象要素＋周辺（§5.8）を three.js の軽量ビューアで表示する。**対象は赤、周辺はグレー**。カメラは対象全体が収まる位置に自動で置く（OrbitControls で操作可能）。
- OBJ モード中は APS Viewer 側のラベル・引き出し線・フォーカスピン・範囲パネル・読み込み表示をすべて隠す。
- three.js（obj-viewer.js）は **OBJ モードが初めて必要になった時点でだけ読み込む**（初回表示の軽さのため）。読み込みに失敗した場合はステータス欄にその旨を出す。
- 抽出結果は Issue 単位で画面側にもキャッシュする。対象要素がない Issue、抽出に失敗したモデル（DACH／sample_architecture）では、理由をメッセージ表示する。

## 7. 既知の制限・未対応

- **Issue の削除は API にない**。削除は Forma の画面からのみ可能（2026-11-16 に画面操作で旧 Issue 19件を削除した実績あり）。
- **スナップショットは API で生成できない**（§5.7）。API 起票の Issue にはスナップショットが付かない。
- **OBJ 抽出は DACH と sample_architecture で失敗する**（変換自体が「No Geometries to extract」。ファイル固有）。
- **形状を持たない要素**（プロパティ DB にはあるがビューアブルの SVF に描画実体がない要素）には、検証可能なピン座標が得られないため正しくピンを置けない（旧 #21・#23 が該当し、作り直しをせず削除した）。
- 要素索引は §2 の前提に対する例外として残っている（付与の動的化は未決）。
- **バージョン間 Diff の比較ペアは「ピン時点 → 最新」に固定**（§5.9）。任意の2版を選んで比べる機能は sample-d には無く、履歴グラフ（別アプリ）側の担当。
- **Diff の結果キャッシュは版番号がキー**：同じ版番号のままファイルが差し替えられた場合、古い結果を読み続ける可能性がある（版番号が上がれば新しいペアとして取り直す）。
- **変更判定はヒューリスティクス**：形状ハッシュ・bbox・値の実質変化で判定しており（§5.9）、要素の削除→再作成（ID の変化）は「削除＋追加」として現れる。プロパティの変更一覧は補助情報で、キー自体の付け替えが残る場合は値の移行が「（なし）→ 値」と表示されることがある。
- **SVF2 座標系ピンの変換は限定的**（§6.4）：変換が効くのは「対象要素が表示モデル内に無い」ピンだけ。要素が解決できる API 起票ピン（#44〜47）は、読み込み完了後に要素ボックスへ付け直されるが、読み込み中の先行表示は変換前の座標のまま一時的にずれる。pinFrame の変換値は snowdonarch の V1 に対して実測したもので、他モデル・他バージョンでは未検証。
- Issue の取得は最大200件まで（ページングの上限）。
- この VM のブラウザからは Viewer の CDN に到達できないため、実機確認はユーザーのブラウザで行う（ローカル検証はオフラインのリグで代替する）。

## 8. 運用

- 起動：`cd demo-issues-3d/app && node server.mjs`（http://localhost:3000）。サーバーは VM の再起動等で止まるため、その都度起動する。
- トークンが失効した場合：sample-a の手動ログインフロー（login-manual）で再ログインし、新しい `.token.json` を **app と sample-a の両方**へコピーしてからサーバーを再起動する（refresh のローテーションは単一チェーンで維持する）。
- リポジトリへの反映：`github/push-sampled.py` で `tkhashi/Autodesk.Sandbox` の `sample-d-issues-3d/` へ push する（`cache/`、`node_modules/`、`.env`、`.token.json` は除外）。
